## 다음 배포 전 수정할 항목

### R01. Markdown 미리보기의 스크립트 실행

- 위치: [public/app.js](../public/app.js):2413–2421, [server.js](../server.js):636–667, 1413–1417.
- `marked.parse(body)` 결과를 그대로 `innerHTML`에 넣는다. 다운로드한 문서나 저장소의 Markdown에도 HTML 이벤트 핸들러가 들어갈 수 있다.
- 별도 개발 포트에서 임시 `.md`를 열었다. 이미지 오류 이벤트가 화면에 `MARKDOWN_SCRIPT_EXECUTED` 문자열을 삽입하는 것을 Chrome에서 확인했다. 파일 변경이나 외부 통신을 수행하는 코드는 사용하지 않았다.
- 이 스크립트는 파일 API와 같은 origin에서 실행된다. 따라서 미리보기 문서가 사용자의 파일 읽기·변경 API를 호출할 수 있는 구조다. 파일 API 호출까지 연결한 재현은 하지 않았다.
- 개선: 렌더링 결과의 HTML 정화, 이벤트 속성·위험 URL 차단, 스크립트 권한이 없는 미리보기 격리를 적용한다. `/api/file`의 HTML/SVG 직접 열기에도 같은 원칙을 적용한다.
- 완료 기준: 이벤트 속성·스크립트 URL·SVG 등을 포함한 문서를 표시해도 스크립트가 실행되지 않으며, 코드 하이라이트와 일반 링크는 정상 동작한다.

Marked 자체는 HTML을 정화하지 않는다고 명시한다. 파서 업그레이드만으로 해결되는 문제가 아니다. [Marked 공식 문서](https://marked.js.org/#usage)

### R02. Git 변경 취소가 선택 범위를 벗어남

- 위치: [server.js](../server.js):1112, 1149; UI [public/app.js](../public/app.js):2977.
- `git checkout -- <paths>`에서 파일명을 literal pathspec으로 처리하지 않는다.
- 임시 저장소에서 `a*.txt`와 `abc.txt`를 수정한 뒤 `a*.txt` 하나만 변경 취소했다. 실제 API는 200을 반환했고 두 파일의 편집이 모두 사라졌다.
- 개선: Stage/Unstage에 이미 적용한 literal 경로 처리를 Git의 다른 파일 경로 작업에도 통일한다.
- 완료 기준: `*`, `?`, `[]`가 포함된 이름을 선택해도 미선택 파일의 편집이 보존된다.

### R03. 동시 이동에서 목적지 이름 충돌

- 위치: [server.js](../server.js):298–301, 309–310.
- 각 전송 요청 내부는 순차 처리하지만 서로 다른 요청은 동시에 실행된다. `uniqueDest()`로 이름을 고른 뒤 실제 `rename()`까지 목적지를 확보하지 않는다.
- VM에서 실제 `transferItems()`를 병렬 호출하고, 두 호출이 같은 목적지를 선택하도록 rename 직전 순서를 맞춘 뒤 실제 파일 연산을 실행했다. 두 작업 모두 `completed`, 원본 두 개 모두 사라짐, 목적지에는 마지막 파일 하나만 남는 결과를 확인했다. 별도 HTTP 요청이나 네이티브 두 창을 통한 재현은 아니다.
- 개선: 목적지 선택과 최종 반영을 함께 보호한다. 앱 내부에서는 대상 폴더별 작업 조정이 필요하고, 외부 프로그램과의 경합까지 고려한 덮어쓰기 금지 방식도 필요하다. EXDEV 임시 복사 후 최종 반영에도 적용한다.
- 완료 기준: 같은 이름을 동시에 이동해도 두 내용이 모두 보존되거나 한 작업이 명시적으로 실패한다. 실패 작업의 원본은 남아야 한다.

### R04. 늦은 응답이 다른 폴더의 목록을 덮어씀

- 위치: [public/app.js](../public/app.js):224–258. 관련 함수: `runSearch()`, `refreshAndSelect()`.
- 실제 함수를 추출한 VM에서 A 폴더 새로고침 시작 → B 폴더 이동 완료 → A 응답 도착 순서를 만들었다. `state.cwd`는 `/B`인데 목록은 `/A/a`가 되는 것을 확인했다.
- 사용자가 보고 있는 주소와 선택·조작하는 파일이 달라질 수 있다. 네트워크 볼륨이나 자동 새로고침에서 특히 확인할 필요가 있다.
- 개선: 탐색·검색·새로고침에 공통 요청 세대와 폴더 검증을 두고 오래된 응답을 무시한다. 미리보기·VCS 조회에도 같은 수명 관리 원칙을 적용한다.
- 완료 기준: 역순 응답, 검색 중 폴더 이동, 자동 갱신 중 탐색에서도 주소·목록·선택·VCS 상태가 같은 폴더를 가리킨다.

### R05. 업데이트 파일 검증과 복구 부족

- 위치: [native/main.swift](../native/main.swift):419–426, 433–454; [install.sh](../install.sh):21–22.
- 업데이터는 `ditto` 종료 코드를 확인하지 않고 `.app` 디렉터리가 있으면 적용한다. 설치 스크립트도 예상 앱의 유효성을 확인하기 전에 기존 앱을 삭제한다.
- 임시 ZIP의 일부 엔트리에 지원하지 않는 압축 방식을 넣자 `ditto`가 종료 코드 1을 반환했지만 `.app` 디렉터리는 남았다. 현재 검사는 이를 통과시킨다. 실제 설치된 앱을 교체하지는 않았다.
- 개선: 압축 해제 성공, 번들 ID·버전·필수 실행 파일을 확인한다. 배포물의 해시·서명 검증 정책도 정한다. 새 앱을 준비한 뒤 교체하고 실행·서버 정상 응답을 확인한 다음 이전 앱을 정리한다.
- 완료 기준: 손상된 ZIP, 잘못된 번들, 복사 실패, 새 앱 실행 실패에서 기존 앱을 계속 사용할 수 있거나 자동 복구한다.

### R06. 백그라운드 업데이트가 작업 도중 재시작

- 위치: [native/main.swift](../native/main.swift):389–392, 443–451, 537–539.
- 시작 5초 후와 4시간 주기의 검사는 새 버전을 발견하면 즉시 적용한다. 파일 전송·VCS 작업·작성 중인 커밋 메시지를 확인하지 않고 서버를 종료하고 앱을 재시작한다.
- 무조건 적용하는 제어 흐름을 확인했다. 실제 사용자 작업을 중단하는 실험은 하지 않았다.
- 개선: 다운로드와 적용을 분리하고 작업 완료 후 적용하거나 사용자가 재시작 시점을 선택하게 한다. 서버 종료는 보유한 PID와 정상 종료 절차를 사용한다.
- 완료 기준: 복사·이동·커밋 중에는 적용이 보류되며, 재시작 전에 진행 상태와 입력 내용이 보존된다. README의 업데이트 설명도 실제 정책과 일치해야 한다.

### R07. 릴리스 태그와 배포물 불일치

2026-09-19 수정: clean main·도구·인증·증가 버전·중복 태그 사전 검사, 빌드 전 버전 커밋,
빌드 후 소스/HEAD 재검사, 동일 커밋 태그와 원자적 푸시를 적용했다. Release 업로드 뒤 feed를 게시한다.
`tests/deploy.test.js`에서 실패 단계별 중단과 소스/태그 일치를 검증한다. 아래는 수정 전 기록이다.

- 위치: [deploy.sh](../deploy.sh):24, 32–35.
- 변경된 작업 트리로 빌드한 다음 `VERSION`, `latest.json`만 추가해 커밋·태그를 만든다. 현재처럼 수정한 소스가 Stage되지 않은 상태이면 ZIP에는 새 코드가 들어가고 태그에는 빠진다.
- 임시 Git 저장소에서 실제 스크립트를 실행하되 빌드는 파일 복사로, 원격 푸시와 GitHub 호출은 모킹했다. 스크립트는 성공했지만 ZIP의 소스는 새 내용, 태그의 소스는 이전 내용이었다. 실제 배포는 하지 않았다.
- 개선: 배포 시작 전에 작업 트리·브랜치·도구·테스트 상태를 확인한다. 확정 커밋에서 빌드하고 그 커밋을 태그로 남긴다. 커밋 실패를 무시하는 `|| true`와 기존 태그 강제 이동도 제거한다.
- 완료 기준: dirty 상태에서는 버전 변경·빌드 전에 중단한다. ZIP의 빌드 ID와 태그 커밋이 일치하며 실패 시 완료로 표시하지 않는다.

### R08. 로컬 API 요청의 신뢰 경계 누락

- 위치: [server.js](../server.js):1466–1475, 1263–1265, 1413–1417, 892–913.
- 라우터는 Host/Origin과 HTTP 메서드를 검사하지 않는다. 변경 API는 Content-Type을 확인하지 않고 본문을 JSON으로 해석한다.
- 실제 `handleRequest`에 외부 Origin과 `text/plain` 본문을 전달했을 때 임시 파일 쓰기가 성공했다. GET `/api/upload`도 빈 파일을 생성했다.
- 실제 외부 웹페이지에서 브라우저를 거쳐 호출하는 경로는 재현하지 않았다. 브라우저별 로컬 네트워크 접근 정책에 따른 차이가 있다. 서버가 요청을 허용한다는 사실을 확인한 결과다.
- 개선: 읽기/쓰기 메서드 명시, JSON 요청 타입 검증, 허용 Host/Origin, 앱 세션 인증을 적용한다. 브라우저 UI와 Swift 클라이언트를 함께 변경해야 한다. 이는 R01의 같은-origin 스크립트 실행도 별도로 막아야 완성된다.
- 완료 기준: GET 쓰기 요청과 허용하지 않은 출처·인증 없는 변경 요청을 거부하고 정상 UI·Finder 드롭은 유지한다. README의 “외부 접근 불가” 설명은 loopback 바인딩의 범위를 정확히 설명하도록 고친다.

### R09. Git/SVN 취소의 표시와 실제 동작 불일치

- 위치: [server.js](../server.js):1254; [public/app.js](../public/app.js):423–425, 479–495.
- 요청 본문을 읽은 후 `req.close`를 구독해 자식 프로세스를 종료하려 한다. 이 시점에 해당 이벤트가 이미 발생해 응답 연결 종료를 놓친다.
- 실제 `api.vcsstream`을 임시 HTTP 서버에서 실행하고 Git 대신 0.5초짜리 무해한 프로세스를 연결했다. 첫 출력 후 연결을 끊어도 종료 요청 0회, 프로세스는 정상 완료했다.
- 개선·완료 기준: 응답 연결 수명에 맞춰 취소를 전달하고 실제 종료를 확인한다. 후속 명령도 시작하지 않아야 한다. UI는 취소 요청 중과 종료 확인을 구분한다. 이미 수행한 Git/SVN 변경의 복원은 별개다.

### R10. 미리보기 스트림 오류로 서버 전체 종료

- 위치: [server.js](../server.js):640–667.
- `stat()` 성공 후 파일이 사라지면 `createReadStream()`의 비동기 오류가 발생한다. 오류 리스너가 없어 바깥 `try/catch`가 처리하지 못한다.
- 격리 프로세스에서 stat 직후 임시 파일을 삭제해 `Unhandled 'error' event`, `ENOENT`, 종료 코드 1을 확인했다.
- 개선·완료 기준: 스트림 오류·연결 종료 처리를 추가하고 해당 요청만 실패하게 한다. 미리보기 중 파일 삭제 후에도 다음 API 요청이 정상 응답해야 한다.

### R11. 이름 변경 시 끊어진 심볼릭 링크 소실

- 위치: [server.js](../server.js):1295–1297.
- `existsSync()`는 끊어진 링크를 없는 경로로 판단한다. 그 이름으로 일반 파일을 변경하면 기존 링크가 덮어써지는 것을 재현했다.
- 개선·완료 기준: 전송의 `uniqueDest()`처럼 `lstat`으로 점유 여부를 확인하고 R03의 충돌 보호 정책을 공유한다. 대상 링크를 보존하며 충돌을 알려야 한다.

### R12. 업로드 실패 후 부분 파일 잔류

- 위치: [server.js](../server.js):903–915.
- 본문의 일부를 보낸 후 연결 오류를 주입하자 실패를 반환하면서 부분 파일은 최종 이름으로 남았다. 쓰기 스트림도 정리되지 않았다. 성공 응답 역시 충돌 회피 후의 `dest` 대신 원래 `target`을 반환한다.
- 개선·완료 기준: 임시 파일로 수신하고 성공 시 최종 위치에 반영한다. 취소·오류 때 스트림과 임시 파일을 정리한다. 응답의 경로는 실제 생성된 파일과 일치해야 한다.

### R13. 업데이트된 앱과 이전 서버가 혼재

- 위치: [native/main.swift](../native/main.swift):543–554, 572; [server.js](../server.js):520.
- 앱이 종료되어도 서버는 살아 있다. 다음 앱은 `/api/home`의 200 여부만 보고 재사용하므로 DMG 수동 교체나 새 개발 빌드 실행 후에도 이전 UI/API가 남을 수 있다.
- 이는 앞서 나온 “업데이트 되나?” 증상을 조사할 때 확인할 경로다. 현재 사용자의 화면 문제가 이 원인이라고 확정한 것은 아니다.
- 개선·완료 기준: 앱과 서버의 버전·빌드 ID·인스턴스를 비교한다. 불일치 시 진행 중 작업을 보존한 뒤 해당 서버를 교체하고, 정보 화면에서 두 버전을 확인할 수 있게 한다.

### R14. Finder 드롭의 실패 결과 누락

- 위치: [native/main.swift](../native/main.swift):227–239; [server.js](../server.js):324.
- Swift 콜백이 통신 오류·HTTP 상태·JSON을 모두 무시하고 새로고침만 한다. HTTP 200이면서 `ok:false`인 부분 실패도 알리지 않는다.
- 개선·완료 기준: 브라우저 붙여넣기와 같은 항목별 결과를 표시한다. 읽기 전용 대상·일부 원본 누락·공간 부족에서 실패 파일과 재시도 방법을 보여준다. 실제 네이티브 실패 실험은 하지 않았다.

### R15. 외부 페이지에 네이티브 브리지 노출

- 위치: [public/app.js](../public/app.js):1542–1546; [native/main.swift](../native/main.swift):248–275, 285–286, 585.
- 웹 링크 바로가기도 동일한 WKWebView 설정으로 열며, 메시지 처리 시 발신 origin·프레임을 검사하지 않는다. 외부 페이지에도 창 열기·닫기·업데이트 확인·드래그 브리지가 제공되는 구조다.
- `fxDrag`에는 마우스 버튼 조건이 있다. 사용자 동작 없이 임의 파일을 읽을 수 있다고 확인한 결과는 아니다. 외부 페이지에서 네이티브 동작을 실제 실행하지 않았다.
- 개선·완료 기준: 외부 링크는 기본 브라우저 또는 브리지 없는 별도 뷰에서 연다. 네이티브 콜백은 허용한 로컬 origin과 프레임만 받으며, 탐색으로 origin이 바뀌어도 권한이 남지 않아야 한다.

## 사용성과 유지보수 개선 제안

아래는 위의 재현된 결함과 구분한 후속 제안이다. 성능 문제를 실측한 결과는 아니다.

| 순서 | 제안 | 기대 효과 / 확인 방법 |
| --- | --- | --- |
| 1 | 파일 작업 목록에 진행률·부분 실패·재시도·최근 결과를 통합 | 두 창 작업과 네이티브 드롭 결과를 일관되게 확인. R03·R06·R14와 함께 설계 |
| 2 | Git Stage 창에 실제 diff와 커밋 직전 상태 갱신 추가 | 무엇을 커밋하는지 확인. 다른 창·터미널에서 index 변경 후 목록과 실제 커밋 대상 비교 |
| 3 | Git 그래프 추가 페이지 조회와 필터 | 현재 최근 100개 고정에서 오래된 이력도 탐색. SVN 로그의 기존 추가 조회 UX와 정렬 |
| 4 | 앱 정보에 앱/서버 버전, 빌드 ID, 업데이트 상태 표시 | 소스 수정·빌드·설치·배포 상태를 구분하고 이름/업데이트 혼선을 진단 |
| 5 | 큰 폴더와 네트워크 볼륨 성능 측정 후 목록 가상화·메타데이터 동시성 제한 검토 | 1천/1만 항목에서 첫 화면 시간, 스크롤, 메모리와 요청 수를 측정하고 필요에 따라 적용 |
| 6 | 파일 작업·VCS·미리보기·업데이터를 기능별 모듈로 점진 분리 | 경로 처리와 작업 수명 계약을 한 곳에서 관리. 새 프레임워크 도입 없이 시작 가능 |
| 7 | 실제 HTTP·브라우저·업데이트 실패 테스트와 자동 검사 추가 | 현재 VM 중심 테스트에 빠진 요청 연결 수명·DOM 실행·압축 실패를 검증 |

Stage/Unstage의 literal 경로, 최초 커밋 전 Unstage, rename 해제, 부분 stage 분리,
index만 커밋하는 흐름에서 이번 검토로 새 핵심 결함은 확정하지 않았다.
다만 Git 모달은 초기 조회와 자체 작업 이후에 갱신되므로 외부 index 변경을 따라가도록 보완할 필요가 있다.
